# 프로젝트 해체 분석과 포트폴리오 심화

## 전체 지도와 분석 범위

먼저 무엇을 만드는 서비스인지, 누가 어떤 요청을 하는지, 중요 요구사항과 제약이 무엇인지 설명한다. 디렉터리 이름보다 실제 실행점·호출·설정·DDL을 근거로 다음 범위를 지도에 표시한다. 존재하지 않는 기술이나 구성 요소를 채워 넣지 않는다.

| 영역 | 복원할 내용 |
| --- | --- |
| 제품·도메인 | 요구사항, 정상/실패 시나리오, 상태 전이, 객체 책임, 불변식 |
| 구조·의존 | 실행 프로세스, 모듈, DI, 외부 연동, 데이터 소유권, 동기/비동기 경계 |
| 데이터 | 논리 관계와 실제 DDL, 제약·인덱스, 조회/갱신, 데이터 수명 |
| 실행·내부 원리 | 사용자 행동/API부터 보안·유스케이스·트랜잭션·SQL·응답까지 |
| 운영 | 빌드·배포·네트워크·설정, 로그·지표, 장애·복구, 테스트 보장 범위 |
| 설계 역사 | 최초 선택, 대안, 실패, 후속 교정, 유지·보류된 이유 |

전체 구조에는 필요한 Context/Container/Component, 데이터에는 ERD, 실행에는 시퀀스·상태 비교를 선택한다. 그림마다 동일 템플릿을 강제하지 않는다. 요청 하나를 깊게 추적하면서 연관된 원리를 설명하고 다시 전체 지도에 위치시킨다. 분석 깊이는 전체 지도 → 기능 추적 → 중요 선택 심화로 조절한다. 독립 재설계나 코드 변경은 명시적으로 요청됐을 때 별도 작업으로 다룬다.

## 쉬우면서 깊은 설명

예를 들어 결제 분석에서는 먼저 “고객에게 결제 성공이 표시됐지만 주문 저장은 실패할 수 있다”는 구체적 문제를 제시한다. 실제 호출·DB 트랜잭션·외부 결제 경계를 코드로 따라간 뒤, 왜 로컬 트랜잭션만으로 외부 효과를 되돌릴 수 없는지 설명한다. 마지막으로 현재 구현이 무엇을 보장하고 무엇은 보장하지 않는지 연결한다. 이는 설명 구성 예시이며 해당 프로젝트가 결제·Outbox·보상을 구현했다는 뜻이 아니다.

코드 발췌에는 경로·심볼·리비전을 붙인다. 의사코드는 실제 구현과 구분한다. 핵심 용어를 상황에 연결하고 입력 → 분기 → 상태 변화 → 결과를 설명한다. 초보자를 이유로 중요한 예외·경계·제약을 생략하지 않되, 관련 없는 Java 기초를 길게 반복하지 않는다.

## 포트폴리오 후보 선별과 심화

기술이 유명하다는 이유로 주제를 고르지 않는다. 다음 기준으로 후보의 중요도와 근거 강도를 설명하고, 근거가 강하거나 중요한 미해결 위험이 있는 주제를 우선한다.

- 실제 사용자 문제·비기능 요구·도메인 불변식과 연결되는가?
- 여러 선택지 사이의 정합성·성능·복잡성·운영 비용 차이를 설명할 수 있는가?
- 구현 경계, 실패 사례, 테스트·측정 조건과 결과를 확인할 수 있는가?
- 사용자의 역할·판단·AI 도움의 범위를 확인할 수 있는가? 확인되지 않은 기여는 추정하지 않는다.

선정된 주제는 **문제와 제약 → 단순 접근의 한계 → 실제 선택 → 내부 동작 → 비교 가능한 대안 → 얻은 점과 비용 → 실패·교정 → 검증과 잔여 한계**로 풀어 쓴다. 대안은 관련 있는 것만 선택하며 마이크로서비스·Kafka·Redis 등의 도입을 정답으로 강요하지 않는다. 기록된 과거 대안과 지금 제안한 대안을 분리한다.

예: 중복 요청과 멱등성, 재고 경쟁과 잠금, 트랜잭션 경계와 외부 효과, N+1/인덱스와 실행계획, 캐시 일관성, 권한·소유권, 배포·롤백·관측성. 실제 코드·제약에 없는 문제를 포트폴리오 소재를 위해 만들어 내지 않는다.

## 증거와 성과 표현

각 핵심 주장 가까이에 코드·테스트·PR·실측 링크를 둔다. 수치는 데이터 규모·동시성·환경·측정 방법·기준선·변경 후 결과·한계를 함께 확인한 경우에만 성과로 쓴다. CI 통과는 성능 개선·운영 검증·사용자 기여의 증거가 아니다. AI가 작성한 코드의 이해와 사용자가 직접 수행한 설계·구현·실험을 구분한다.

면접에서 설명할 수 있는 논리 구조를 정리할 수 있지만, 허위 성과 문장이나 사용자가 하지 않은 일을 한 것처럼 쓰지 않는다. 자료가 부족하면 “포트폴리오 후보, 실측 미확인”처럼 남기고 필요한 검증을 제안한다. 읽기 전용 분석 중 부하·장애·마이그레이션 실험을 자동 실행하지 않는다.

## 완료 점검

전체 범위의 조사 상태, 실제 정상/실패 경로, 상태·트랜잭션·데이터 경계, 설계 이유의 근거 수준, 대안의 비용, 포트폴리오 심화 근거, 남은 미확인을 확인한다. 단순 파일 해설·근거 없는 설계 의도·조건 없는 성능 수치·모든 영역 완료 주장이 남아 있으면 수정한다.
