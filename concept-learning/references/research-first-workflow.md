# 조사 우선 강의 작성 워크플로 — Research Before Writing

**적용 대상:** `concept-learning`이 본격적인 Java/Spring/백엔드 기술 강의를 작성할 때 적용하는 **작성 전 필수 작업**이다. 질문이 짧은 즉답이거나 사용자가 코드만·검색 없이·이미지 없이 등 범위를 지정했으면 적절하게 축소한다. 이 문서는 스킬의 자연어 실행 지침이며, 별도 검색 엔진이나 백그라운드 실행·강제 후크를 추가하지 않는다.

## 단계 A — 주제 분석: 검색어부터 설계

1. **학습 요청을 정확히 좁힌다.** 사용자가 지정한 주제와 알려진 Java/Spring/DB 버전·교재 범위를 확인하고 새 로드맵을 만들지 않는다. 대상으로 삼을 수준은 **신입~2년 차 실무 개발자**이며 입문 문법 설명의 반복을 피한다.
2. 주제를 **핵심 메커니즘(실행·상태 변화), 설계 적용과 트레이드오프, 실무 경계 조건, 관련 심화 개념**으로 나눈다. 각 부분에 필요한 의문을 구체적 검색어로 바꾼다. 예를 들어 단순히 '자바 다형성'만 반복 검색하지 않고 '컴파일타임 vs 런타임 의존성', '메서드 디스패치', '인터페이스의 행동 계약', 'LSP 치환 가능성'처럼 탐색 범위를 넓힌다.
3. **탐색 전부터 긴 설명이나 코드 작성에 착수하지 않는다.** 우선 자료의 존재와 주제 적합성을 조사하여 설명의 깊이와 구조를 결정한다.

## 단계 B — 공개 참고 자료·서적·실제 이미지 선조사

1. **공개 기술 자료:** 한국 개인 개발 블로그(Tistory·Velog·GitHub.io·Medium·독립 블로그), 테코블(Tecoble), 한국 IT 기업 기술 블로그를 **핵심 개념별로 검색어를 바꾸어 탐색**한다. 검색 결과 제목만 보고 인용하지 않고 **실제로 열어 읽은 내용**, 기술 버전, 코드/사례·조건과 현재 개념과의 관련성을 검토한다. 공식 명세·레퍼런스로 사실을 교차 검증한다. 한국어 출판사 기사(한빛미디어)나 위키독스 추천은 제외한다.
2. **서적을 심화 탐색의 단서로:** 해당 분야의 널리 쓰이는 기술 서적의 **공개 목차·저자 글·허용된 미리보기·실제 읽은 공개 서평·독서 정리 글**을 조사한다. 전문을 열지 않았다면 '책에서 직접 확인한 사실'이라고 쓰지 않는다. 검증된 공개 글에서 소개하는 설계 문제·용어·관점을 다음 검색어로 사용한다. 전문 문단·이미지·표를 무단 복제하지 않는다.
3. **이미지를 별도 조사 작업으로 수행:** 구조/상태/시퀀스의 그림이 학습에 도움이 되는 각 핵심 부분에서 가능한 이미지 검색을 실행하고 **원문 글에 실제 포함된 개념도·메모리/객체 관계·메서드 호출/실행 그림**을 확인한다. 후보 그림의 실제 개념 적합성, 원본 URL, 설명 포인트, 이용 허락/표시 가능성을 검토한다. **파비콘, 출처 로고, 표지, 사이트 미리보기, 빈 `[image]`, 존재하지 않는 도식의 캡션은 후보에서 제외**한다. 이미지 검색 결과를 단순히 열었다고 사용자에게 그림이 표시된 것으로 취급하지 않는다.
4. **자료 폭을 검토:** 출처가 특정 사이트의 한두 글이나 입문형 정의에만 편중되면 다른 검색어·개인 블로그·테코블·기업 블로그를 재탐색한다. 중요한 주제는 가능한 범위에서 **둘 이상의 독립적 관점 또는 출처 유형**을 비교한다. 자료의 다양성을 위해 관계없는 글이나 불확실한 이미지를 억지로 삽입하지 않는다.

### Java 다형성의 예시 탐색 지형 — 목록 복사가 아닌 검색 힌트

| 탐색 분야 | 예시 키워드 | 설명에 연결할 질문 |
| --- | --- | --- |
| Java 메커니즘 | 다형적 참조, 업캐스팅, 오버라이딩, 동적 디스패치, 컴파일 시점 타입 | 호출 가능 메서드와 실제 실행 구현을 어떻게 구분할까? |
| 협력과 설계 | 역할·책임·협력, 메시지와 메서드, 행동 계약, 대체 가능성 | 같은 요청을 여러 객체가 처리할 때 협력을 어떻게 유지할까? |
| 의존성과 확장 | 컴파일타임 의존성, 런타임 의존성, 인터페이스, OCP, DIP, 합성 | 변하는 구현을 분리할 때 무엇이 안정적인가? |
| 조건문·타입 검사 | `instanceof`, 조건문 분기, Tell Don't Ask, LSP | 타입별 조건 처리가 언제 필요한가? |
| 심화 서적 | **《오브젝트》**, **《객체지향의 사실과 오해》**, 공개 목차·독서 해설 | Java 문법을 넘어 책임·메시지·유연성의 설계적 의미를 어디서 더 배울까? |
| 실제 이미지 | 오버라이딩·동적 바인딩 구조, 실제 객체 참조, 인터페이스 구현 다이어그램 | 그림이 현재 코드의 어떤 실행/타입 관계를 보여줄까? |

**주의:** 위 책과 키워드는 **객체지향/다형성 요청에 관련된 후보**다. 특정 책이 어떤 장에서 무엇을 말했다고 인용하려면 실제 공개된 근거를 먼저 확인한다. JPA/MVCC/Linux 등의 다른 강의에 무관한 책·예시를 반복하지 않는다.

## 단계 C — 내부 근거 지도(evidence map) 구성

**강의 본문을 작성하기 전에** 다음 정보를 내부적으로 각 중요한 소제목에 연결한다. 이 표는 모델의 검토용이지 자동으로 사용자가 보게 될 결과물이 아니며, 외부 DB/파일에 자동 저장하지 않는다.

| 내부 항목 | 기록할 내용 |
| --- | --- |
| 설명할 핵심 질문 | 해당 부분에서 반드시 해소할 메커니즘/설계 판단 |
| 확인된 참고 글 | **실제로 열어 읽은** URL·주장·코드/사례·버전/한계 |
| 기술적 검증 | 공식 문서/명세와 일치하는 사실, 아직 미검증인 해석 |
| 서적/심화 연결 | 공개적으로 확인한 목차·저자·독서 해설의 **검색 단서**와 후속 키워드 |
| 이미지 상태 | **FOUND_AND_DISPLAYABLE / FOUND_LINK_ONLY / NOT_FOUND / NOT_APPLICABLE / TOOL_UNAVAILABLE** + 원본·내용·권리 |
| 본문 계획 | 핵심 코드·설명 깊이·참고 링크·이미지 위치·중복될 내용 제거 |

1. 소제목별 출처와 주장의 직접적인 관련성을 확인한다. **중요한 부분이 빈약하면 먼저 추가 검색**하고, 실제 읽지 않은 제목만 배치하지 않는다.
2. 그림이 필요한데 후보가 없다면 **별도의 관련 이미지 검색을 시도**한 상태인지 먼저 점검한다. 찾았어도 이용·삽입이 불가능하면 `FOUND_LINK_ONLY`로 기록하고 실제 이미지 대신 원문 링크와 내용 안내를 선택한다. 도식을 자동 생성하는 지름길을 택하지 않는다.
3. 발견된 참고 자료가 현재 주제에서 중요하게 다룰 개념을 바꾼다면 **소제목과 예제 순서를 이 단계에서 수정**한다. 적절한 조사 근거가 없는 주변 이야기를 길게 늘리지 않는다.

## 단계 D — 근거 기반 작성 및 후속 품질 게이트

1. **그제서야** 본문을 작성한다. 새 개념의 짧은 정의, 실제 실행 과정, 반례·한계·설계 트레이드오프에 집중한다. 각 주요 소제목 근처에 관련 한국어 기술 글의 **실제로 확인한 핵심 내용과 링크**를 붙인다. 출처를 마지막에 몰아넣지 않는다.
2. 그림을 실제로 보여줄 수 있는 플랫폼과 권리 범위라면 해당 **원본 개념 이미지**를 설명 가까이에 보여주고 본문에서 핵심을 해설한다. 보여줄 수 없다면 실제 표시한 것으로 주장하지 않는다.
3. **답변 품질 게이트의 G0~G8**을 적용한다. 사전 조사·이미지 확인·근거 매핑이 생략된 상태는 `PASS`가 아니다. 불합격이면 **단계 B/C로 되돌아가 다시 조사한 다음** 부분 수정 및 재검증한다. 이용 제한·도구 미제공 등으로 해결 불가한 경우에만 `LIMITATION`으로 구분하고 오도하지 않는다.
4. 짧은 요청이나 특정 자료 범위 제한이 있다면 주제와 사용자 지시에 맞게 검색 깊이를 축소한다. 별도 승인 없이 장기간 비동기 조사·외부 저장·진도 관리·Wiki/Obsidian 게시를 하지 않는다. 가능한 자료가 없다면 알고 있는 사실을 설명하되 확인되지 않은 참고/그림을 꾸며내지 않는다.

**운영 원칙:** 조사에 실패했는데 '참고 자료를 풍부하게 반영했다'고 주장하지 않는다. 반대로 방대한 자료를 모으는 것 자체가 목적이 아니다. **증거가 설명의 구조와 깊이를 바꿀 만큼 충분히 조사한 뒤 필요한 내용만 남기는 것**이 목표다.
