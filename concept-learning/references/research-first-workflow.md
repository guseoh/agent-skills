# 조사 우선 강의 작성 워크플로 — Research Before Writing

**적용 대상:** `concept-learning`이 본격적인 Java/Spring/백엔드 **설명(EXPLAIN)** 또는 **핵심 정리(SUMMARIZE)**를 작성할 때 적용하는 작성 전 작업이다. 모드와 사용자 제약을 먼저 확인하고, 정리 모드는 핵심 사실·직접 관련 자료 위주로 **조사 범위와 글의 길이를 축소**한다. 질문이 짧은 즉답이거나 사용자가 코드만·검색 없이·이미지 없이 등 범위를 지정했으면 적절하게 축소한다. 이 문서는 스킬의 자연어 실행 지침이며, 별도 검색 엔진이나 백그라운드 실행·강제 후크를 추가하지 않는다.

## 단계 A — 요청 모드·주제 분석: 검색어부터 설계

0. **[요청 동사별 응답 모드](response-modes.md)를 먼저 선택한다.** `설명해줘`·`진행하자`는 EXPLAIN, `정리해줘`·`요약해줘`는 SUMMARIZE다. 정리는 필수 메커니즘·구분·주의점 중심으로 범위를 줄이고, 소제목 수부터 늘리지 않는다.
1. **학습 요청을 정확히 좁힌다.** 사용자가 지정한 주제와 알려진 Java/Spring/DB 버전·교재 범위를 확인하고 새 로드맵을 만들지 않는다. 대상으로 삼을 수준은 **신입~2년 차 실무 개발자**이며 입문 문법 설명의 반복을 피한다.
2. 주제를 **핵심 메커니즘(실행·상태 변화), 설계 적용과 트레이드오프, 실무 경계 조건, 관련 심화 개념**으로 나눈다. 각 부분에 필요한 의문을 구체적 검색어로 바꾼다. 예를 들어 단순히 '자바 다형성'만 반복 검색하지 않고 '컴파일타임 vs 런타임 의존성', '메서드 디스패치', '인터페이스의 행동 계약', 'LSP 치환 가능성'처럼 탐색 범위를 넓힌다.
3. **탐색 전부터 긴 설명이나 코드 작성에 착수하지 않는다.** 우선 자료의 존재와 주제 적합성을 조사하여 설명의 깊이와 구조를 결정한다.

## 단계 B — 공개 참고 자료·서적·실제 이미지 선조사

1. **공개 기술 자료:** 한국 개인 개발 블로그(Tistory·Velog·GitHub.io·Medium·독립 블로그), 테코블(Tecoble), 한국 IT 기업 기술 블로그를 **핵심 개념별로 검색어를 바꾸어 탐색**한다. 검색 결과 제목만 보고 인용하지 않고 **실제로 열어 읽은 내용**, 기술 버전, 코드/사례·조건을 검토한다. **주장-출처 적합성 검증:** 현재 소제목에서 설명할 구체적인 사실·코드 동작·설계 선택을 그 글이 **직접 설명하거나 입증하는가**를 확인한다. 예컨대 '정적 메서드는 오버라이딩되지 않는다'를 설명하면서 정적 메서드의 일반적인 활용 장단점만 다룬 글을 해당 언어 규칙의 증거로 삼지 않는다. 이런 글은 다른 관련 소제목에 옮기거나 제외한다. 공식 명세·레퍼런스로 사실을 교차 검증한다. 한국어 출판사 기사(한빛미디어)나 위키독스 추천은 제외한다.
2. **서적은 현재 주제 관련성이 확인될 때만 탐색한다:** 해당 주제를 직접 다루는 기술 서적의 공개 목차·저자 글·허용된 미리보기·실제 읽은 공개 서평·독서 정리 글을 검색 단서로 삼는다. **발견된 관점을 설명 본문의 어느 단원에 연결할지 미리 정하고**, 확인 가능한 새 통찰을 제공하지 못한다면 책 이름을 결론에 장식처럼 추가하지 않는다. **주제 일치 여부를 자료를 찾기 전에 먼저 확인**하고, 연관성이 낮으면 **그 책은 탐색에서 제외**한다. 예컨대 **《오브젝트》·《객체지향의 사실과 오해》는 객체지향·다형성 후보**지만 **Spring Bean 생명주기에서는 기본 탐색 대상이 아니다**. Spring 주제라면 Spring 컨테이너·Bean 초기화·스코프의 공식 문서와 관련된 공개 기술 글을 우선한다. 관련 도서가 아예 없다면 책을 억지로 끼워 넣지 않는다. 전문을 열지 않았다면 '책에서 직접 확인한 사실'이라고 쓰지 않고, 전문 문단·이미지·표를 무단 복제하지 않는다.
3. **이미지를 별도 조사 작업으로 수행:** EXPLAIN의 구조/상태/시퀀스 단원에서 이미지 검색을 실행하고 **원문 글에 실제 포함된 개념도·메모리/객체 관계·메서드 호출/실행 그림**을 확인한다. **이미지 검색 결과의 썸네일, 출처 파비콘, 원문 페이지 링크, 이미지 자체를 넣은 인라인 미디어는 서로 다른 결과물**이다. 지원되는 미디어 표시 방법이 있으면 출처와 이용 조건이 허용하는 범위에서 **실제 개념 이미지를 본문에 삽입**하고, 화면 렌더링을 확인하지 못했다면 사용자에게 표시가 확정됐다고 주장하지 않는다. 후보 그림의 실제 개념 적합성, 원본 URL, 설명 포인트, 이용 허락/표시 가능성을 검토한다. **파비콘, 출처 로고, 표지, 사이트 미리보기, 빈 `[image]`, 존재하지 않는 도식의 캡션은 후보에서 제외**한다. 이미지 검색 결과를 단순히 열었다고 사용자에게 그림이 표시된 것으로 취급하지 않는다.
4. **모드에 맞춰 자료 폭을 검토:** EXPLAIN에서 출처가 특정 사이트의 한두 글이나 입문형 정의에만 편중되면 다른 검색어·개인 블로그·테코블·기업 블로그를 재탐색한다. SUMMARIZE에서는 핵심 사실을 정확히 검증하는 데 필요한 자료만 확인하고, 출처 수를 늘리기 위해 요약을 장황하게 만들지 않는다. 중요한 주제는 가능한 범위에서 **둘 이상의 독립적 관점 또는 출처 유형**을 비교한다. 자료의 다양성을 위해 관계없는 글이나 불확실한 이미지를 억지로 삽입하지 않는다.

### Java 다형성의 예시 탐색 지형 — 목록 복사가 아닌 검색 힌트

| 탐색 분야 | 예시 키워드 | 설명에 연결할 질문 |
| --- | --- | --- |
| Java 메커니즘 | 다형적 참조, 업캐스팅, 오버라이딩, 동적 디스패치, 컴파일 시점 타입 | 호출 가능 메서드와 실제 실행 구현을 어떻게 구분할까? |
| 협력과 설계 | 역할·책임·협력, 메시지와 메서드, 행동 계약, 대체 가능성 | 같은 요청을 여러 객체가 처리할 때 협력을 어떻게 유지할까? |
| 의존성과 확장 | 컴파일타임 의존성, 런타임 의존성, 인터페이스, OCP, DIP, 합성 | 변하는 구현을 분리할 때 무엇이 안정적인가? |
| 조건문·타입 검사 | `instanceof`, 조건문 분기, Tell Don't Ask, LSP | 타입별 조건 처리가 언제 필요한가? |
| 심화 서적 | **《오브젝트》**, **《객체지향의 사실과 오해》**, 공개 목차·독서 해설 | Java 문법을 넘어 책임·메시지·유연성의 설계적 의미를 어디서 더 배울까? |
| 실제 이미지 | 오버라이딩·동적 바인딩 구조, 실제 객체 참조, 인터페이스 구현 다이어그램 | 그림이 현재 코드의 어떤 실행/타입 관계를 보여줄까? |

**주의:** 위 책과 키워드는 **객체지향/다형성 요청에 한정된 예시 후보**이며 **관련 없는 Spring Bean 생명주기·JPA/MVCC·Linux·AI 학습에는 자동으로 사용하지 않는다.** 학습 주제마다 관련 도서를 새로 평가하며, 책이 필요하지 않으면 생략한다. 특정 책의 실제 장·주장을 인용하려면 공개된 근거를 확인한다.

## 단계 C — 내부 근거 지도(evidence map) 구성

**강의 본문을 작성하기 전에** 다음 정보를 내부적으로 각 중요한 소제목에 연결한다. 이 표는 모델의 검토용이지 자동으로 사용자가 보게 될 결과물이 아니며, 외부 DB/파일에 자동 저장하지 않는다.

| 내부 항목 | 기록할 내용 |
| --- | --- |
| 설명할 핵심 질문 | **EXPLAIN**: 해당 부분의 메커니즘/설계 판단. **SUMMARIZE**: 반드시 기억할 핵심 개념·구분·주의점 |
| 확인된 참고 글 | **실제로 열어 읽은** URL·주장·코드/사례·버전/한계 및 **해당 소제목의 어느 주장을 직접 뒷받침하는지** |
| 기술적 검증 | 공식 문서/명세와 일치하는 사실, 아직 미검증인 해석 |
| 서적/심화 연결 | **현재 주제와의 관련성 판단 후**, 공개 목차·저자·독서 해설에서 **검증된 관점·이를 반영할 본문 위치**. 제목/장 번호만 남는다면 제외 |
| 이미지 상태 | **FOUND_AND_DISPLAYABLE / FOUND_LINK_ONLY / NOT_FOUND / NOT_APPLICABLE / TOOL_UNAVAILABLE** + 원본·내용·권리·본문 삽입 여부·코드와의 연결. **발견/링크/삽입/실제 렌더링 확인을 구분** |
| 본문 계획 | 핵심 코드의 **실제 동작 호출·출력/상태 변화**, 설명 깊이·참고 링크·이미지 위치·중복될 주장 제거 |

1. 소제목별 **주장 → 출처 내용 → 본문 설명**의 대응을 확인한다. 한 출처가 한 문장의 주변 주제만 언급할 뿐 실제 메커니즘을 설명하지 않는다면 해당 링크는 근거로 계산하지 않는다. 중요한 부분이 빈약하면 추가 검색·소제목 통합·공식 근거 보강 중 적절한 방법을 택한다. 실제 읽지 않은 제목만 배치하지 않는다.
2. 그림이 필요한데 후보가 없다면 **별도의 관련 이미지 검색을 시도**한 상태인지 먼저 점검한다. 찾았어도 이용·삽입이 불가능하면 `FOUND_LINK_ONLY`로 기록하고 실제 이미지 대신 원문 링크와 내용 안내를 선택한다. 도식을 자동 생성하는 지름길을 택하지 않는다.
3. 발견된 참고 자료가 현재 주제에서 중요하게 다룰 개념을 바꾼다면 **소제목과 예제 순서를 이 단계에서 수정**한다. 같은 '인터페이스를 쓰면 구현 교체가 편하다'라는 결론을 여러 단원에서 반복하지 않도록 **메커니즘 → 실제 협력 → 계약·트레이드오프**로 논점을 나누고, 불필요한 예제는 하나로 통합한다. 적절한 조사 근거가 없는 주변 이야기를 길게 늘리지 않는다.

## 단계 D — 근거 기반 작성 및 후속 품질 게이트

1. **그제서야 모드별 본문을 작성한다. EXPLAIN**에서는 새 개념의 짧은 정의, 실제 실행 과정, 반례·한계·설계 트레이드오프에 집중하고 각 주요 소제목 가까이에 확인한 한국어 기술 글의 내용과 링크를 제공한다. **SUMMARIZE**에서는 핵심 개념·차이·실무 주의점만 정확히 추려 간결하게 정리하고 실제 필요한 출처만 가까이에 붙인다. 출처를 마지막에 몰아넣거나 억지로 채우지 않는다.
2. 그림을 실제로 보여줄 수 있는 플랫폼과 권리 범위라면 해당 **원본 개념 이미지를 실제 미디어 표현으로 본문에 포함**하고, 이미지의 **구체적 화살표/객체/상태가 예제의 어떤 코드·호출에 해당하는지** 해설한다. 원본 페이지나 이미지 파일로 향하는 **텍스트 링크만 있다면 이미지가 표시됐다고 주장하지 않는다**. 보여줄 수 없다면 실제 표시한 것으로 주장하지 않는다.
3. **[요청 모드별](response-modes.md) 답변 품질 게이트의 G0~G8**을 적용한다. 사전 조사·이미지 확인·근거 매핑이 생략된 상태는 `PASS`가 아니다. 불합격이면 **단계 B/C로 되돌아가 다시 조사한 다음** 부분 수정 및 재검증한다. 이용 제한·도구 미제공 등으로 해결 불가한 경우에만 `LIMITATION`으로 구분하고 오도하지 않는다.
4. 짧은 요청이나 특정 자료 범위 제한이 있다면 주제와 사용자 지시에 맞게 검색 깊이를 축소한다. 별도 승인 없이 장기간 비동기 조사·외부 저장·진도 관리·Wiki/Obsidian 게시를 하지 않는다. 가능한 자료가 없다면 알고 있는 사실을 설명하되 확인되지 않은 참고/그림을 꾸며내지 않는다.

**운영 원칙:** 조사에 실패했는데 '참고 자료를 풍부하게 반영했다'고 주장하지 않는다. 반대로 방대한 자료를 모으는 것 자체가 목적이 아니다. **증거가 설명의 구조와 깊이를 바꿀 만큼 충분히 조사한 뒤 필요한 내용만 남기는 것**이 목표다.
