# 한국어 중심 기술 참고 글·국내외 원본 이미지 활용 기준

이 문서는 주제 학습 답변에서 **검증된 기술 내용, 실제 이미지, 선택적 심화 학습**을 효과적으로 사용하는 방법이다. **본문 설명에 인용하는 기술 글과 시각화를 위한 원본 이미지의 출처 기준은 서로 다르다.** 자료의 개수나 글 길이 자체가 목표는 아니다. **반드시 [조사 우선 강의 작성 워크플로](research-first-workflow.md)와 함께 적용하며, 관련 자료/이미지는 본문 작성 전에 탐색한다.**

## 한국어 참고 자료: 개발 기술 블로그 중심

1. **본문 참고 글은 한국어 기술 블로그를 중심으로 선정한다.** 정확한 Java/Spring/JPA/DB/CS 동작은 언어와 관계없이 해당 버전의 공식 명세·벤더 레퍼런스로 검증하되, **학습자에게 제공하는 해설·사례·심화 참고 글의 대부분은 한국어 개인 개발 기술 블로그와 국내 IT 기업 기술 블로그**에서 선정한다. 비율을 기계적으로 채우기 위해 내용이 부정확하거나 무관한 한국어 글을 추천하지 않는다. 해당 주제의 적절한 한국어 자료가 부족하거나 해외 원문이 정확성·전문성을 실질적으로 높이면 해당 외국어 글도 보조적으로 사용하고 한국어로 핵심을 설명한다.
2. **개발자 개인 블로그와 우아한테크코스 기술 글을 필수 후보군에 포함한다.** Tistory, Velog, Medium, GitHub.io, 독립 도메인 및 **테코블(Tecoble, 우아한테크코스 크루 기술 글)**을 대상으로 관련된 한국어 개발 글을 확인한다. 예컨대 사용자가 제시한 [hudi.blog의 객체지향 생활 체조 글](https://hudi.blog/thoughtworks-anthology-object-calisthenics/)은 **객체지향 관련 자료 탐색의 예시**이지 모든 강의에 자동 인용하는 고정 링크가 아니다.
3. **국내 IT 기업 블로그도 같은 비중으로 검토한다.** 우아한형제들·토스·카카오·네이버 등의 기술 블로그는 현재 개념에 직접 관련된 글이 실제 존재할 때 활용한다. 개인 블로그나 회사 블로그라는 이름만으로 정확성이 보장되지는 않는다.
4. **명시적 제외:** 한빛미디어(Hanbit Media)와 위키독스(Wikidocs)의 글·도서 소개·채널 페이지는 **추천 참고 자료 및 참고 링크 후보에서 제외**한다. 한국어 기술 자료를 찾으라는 요청을 출판사 페이지·범용 문서 모음 링크로 대체하지 않는다. 사용자가 해당 문서 자체를 분석해 달라고 명시적으로 제공한 경우에는 그 요청만 별도 처리한다.
5. **내용을 실제로 읽고 검증한다.** 작성 날짜, 기술 버전, 실행 전제, 사실/해석, 코드·실험의 검증 여부를 본다. 개발 블로그의 추측을 언어 명세나 프레임워크 계약처럼 단정하지 않는다.
6. **주장·출처의 직접 대응으로 본문에 융합한다.** 장문 EXPLAIN의 각 주요 소제목 및 독립된 핵심 하위 주제에 대해 **구체적인 주장·코드 동작·설계 판단을 먼저 식별**하고, 그 내용을 실제 설명하는 글을 찾아 검증한다. 주변 주제를 다루는 글을 소제목에 붙였다는 사실만으로 적합한 참고 자료로 취급하지 않는다. 실제 읽은 글이 설명하는 핵심 원리·사례·주의 조건 및 현재 소제목과의 관계를 본문에 녹이고 그 근처에 링크를 제공한다. 도입 또는 결론에만 참고 URL을 몰아넣지 않는다. 같은 URL 반복을 피하고 적합한 글이 없거나 접근이 막히면 검증 범위를 밝힌다. **원문을 열지 않아도 현재 주제의 핵심을 이해할 수 있도록** 실제 확인한 주장을 충분히 설명한다. 짧은 답변에 의미 없는 '소제목별 1개' 형식을 강제하지 않는다.

## 기술 서적·독서 해설을 탐색 키워드로 활용

- **현재 주제 → 직접 관련된 서적 여부 판단 → 관련성이 확인된 서적의 핵심 개념 → 공개 검증 가능 자료** 순서로 탐색한다. 관련 없는 책은 검색에 포함하지 않고, 적합한 책이 없어도 강의/정리를 진행한다. 관련 서적의 공개 목차·저자 글·책 소개·독서 해설은 현재 주제에 **놓친 설계 관점이나 깊이를 발견**하는 데 쓸 수 있다. 공개 자료에 근거하여 추가 검색어를 확장하고 실제 읽은 기술 글·공식 문서로 내용을 검증한다.
- **객체지향·다형성** 학습에서만 예시로 **《오브젝트》**와 **《객체지향의 사실과 오해》**는 역할·책임·협력, 메시지, 컴파일타임/런타임 의존성, 다형성과 치환 가능성 등의 탐색 출발점이다. **Spring Bean 생명주기·트랜잭션·Linux 같은 무관한 주제에는 자동 적용하지 않는다.** **특정 책의 본문을 직접 열지 않았다면** 정확한 원문 인용·장 번호·저자의 주장을 임의로 확정하지 않는다.
- 출판사 한빛미디어와 위키독스는 일반 한국어 기술 글 **추천에서 제외**하되, 사용자가 명시한 특정 책 자체의 개념을 이해하기 위해 **합법적으로 공개된 목차·서평·저자 자료**를 검토하는 행위까지 막지 않는다. 인용은 짧고 적절하게, 허락 없는 본문/이미지 복제는 하지 않는다.

## 시각 자료 출처는 언어·국가 제한 없이 탐색

- **본문 기술 글과 그림의 검색 전략을 분리한다.** 학습에 인용하는 글은 한국어·국내 IT 기업 블로그가 대부분이 되도록 우선하지만, **이미지·구조도·시퀀스 다이어그램·원본 강의 그림은 한국어 자료만으로 제한하지 않는다.** 해외 벤더 공식 문서, 기술 블로그, 공개 강의 자료, 프로젝트 공식 문서 등에서도 **적합한 실제 개념 이미지**를 적극 탐색한다.
- **한국어·영어 검색어를 모두 사용한다.** 예: 'InnoDB MVCC Read View 버전 체인 그림'과 'InnoDB consistent read undo version chain diagram'을 각각 탐색한다. 그림은 출처 국가보다 **구조적 정확성, 현재 코드/주제와의 대응, 해상도와 글자 가독성, 사용·표시 가능 조건**으로 선택한다.
- **이미지의 표시 언어는 한국어·영어로 제한한다.** 검색 대상이 중국·일본 등 해외 자료여도 괜찮지만, 학습 답변에 실제로 보여주는 개념도 안의 **설명 문구·제목·데이터 값의 언어·축 레이블은 한글 또는 영어**여야 한다. 숫자·기호·SQL 식별자·기술 약어 같은 무언어 요소는 예외다. **중국어·일본어 등 다른 언어가 들어간 설명형 그림은 선택하지 않고, 같은 개념의 한글·영어 이미지를 다시 탐색**한다. 해외 원문의 영문 레이블은 원본의 객체·화살표·단계 이름을 현재 설명과 대응시키고 핵심 내용을 한국어로 풀어 준다. 그림의 라벨을 확인 없이 번역·가공하거나, 출처를 숨기거나, 이미지 권리/라이선스를 무시하지 않는다. 영문 그림만 보여주고 해설을 생략하는 것은 실패다.
- **언어별 이미지 수량 목표를 강제하지 않는다.** 이미지 내부에 다른 언어가 없는지 **실제 이미지를 열어 눈으로 확인**한다. 미리보기 제목·페이지 언어만으로 내부 텍스트를 추정하거나 **OCR 검사·번역 성공을 수행한 것처럼 주장하지 않는다.** 한국어 그림이 이미 충분히 좋으면 굳이 해외 그림으로 바꾸지 않는다. 해외 그림이 더 정확하고 선명하면 우선 활용할 수 있다. 실제 사용 가능한 한글·영어 그림이 없는 경우에는 **확인된 원리로 독립적인 단순 도식을 직접 구성하거나 문단·표로 설명**할 수 있다. 원본을 무단으로 그대로 베껴 번역·재게시하거나, 파비콘·사이트 미리보기로 대체하지 않는다.

## 이미지가 최우선, 생성 도식은 보조

1. **본문을 시작하기 전에 한국어·영어를 병행하여 별도의 이미지 탐색을 수행한다.** 검색 원문 국적·언어와 **그림 속 실제 가독 언어를 별도 판정**한다. 객체 참조·협력 관계·JVM 메모리·Spring Bean/프록시·JPA 영속성·DB Lock/MVCC·네트워크 패킷 등 **시각 설명이 유익한 주제는 국내외 실제 관련 이미지부터 탐색**한다. 특히 기술 글 안에 들어 있는 설명 그림, 강의 슬라이드에 실린 이미지, 원리 흐름을 보여주는 구조도가 적합한지 확인한다.
2. **실제 내용 이미지를 본문에 포함하는 단계까지 진행한다.** 이미지 검색·열람 도구를 사용할 수 있으면 원문 글에 들어 있는 **개념 설명 그림·코드 구조도·강의 슬라이드**의 내용을 확인한다. 사용 권한 및 표시 방법이 확인된 경우 **실제 인라인 이미지/지원 미디어 컴포넌트로 소제목 가까이에 포함**한다. **원문 글 링크, 이미지 URL의 텍스트 링크, 이미지 검색 썸네일, 사이트 파비콘, 실제 이미지로 삽입된 결과는 각각 별개**로 판정한다. **Google s2/favicon, 파비콘, 브랜드 로고, 표지, [image]라는 빈 자리, 출처명, 사진이 없는 그림 설명은 이미지 제공으로 인정하지 않는다.** 이미지를 검색했더라도 실제 표시하지 못했다면 표시했다고 주장하지 않는다.
3. **이미지의 실제 요소를 현재 코드와 연결해 해설한다.** 보여준 그림의 객체·참조·호출 화살표·상태·시점 중 **현재 예제의 무엇과 대응하는지** 구체적으로 해설한다. '다형성을 보여주는 그림이다'라는 소개만으로 끝내지 않는다. 원본의 단순화·버전 제약이 있으면 밝힌다.
4. **도식의 남용을 방지한다.** 원본 이미지를 찾지 못했다는 이유로 직접 생성한 박스·화살표 도식이나 텍스트 흐름도를 여러 개 만드는 것은 실패다. 실제 이미지가 설명할 수 없는 한 부분을 표현할 때만 자체 도식을 **보조적으로** 추가한다. 가로형·단순한 흑백 표현을 선호하되 정확성이 우선이다.
5. **저작권·접근 제한을 지킨다.** 출처와 이용 조건을 확인하지 못한 타인의 그림을 무단 복제·재게시하지 않는다. 이미지를 직접 표시할 수 없으면 확인한 **원본 페이지 링크와 그림의 내용을 설명**하거나 독립 도식으로 보완한다. 실제 이미지를 보지 못한 상황에서는 본 적이 있다고 주장하지 않는다.
6. **이미지가 정말 필요하지 않은 주제에는 강제하지 않는다.** 용어의 짧은 정의·간단한 코드 해설처럼 이미지를 넣어도 이해가 나아지지 않는다면 설명과 예제로 충분하다.
7. **이미지 확보·본문 포함·화면 렌더링을 구분한다.** **그림 내부의 주요 문구가 한국어·영어인지 확인한 후보만** 본문 이미지로 채택한다. `FOUND_AND_DISPLAYABLE`(실제 이미지·출처·권리·표시 가능 확인), `FOUND_LINK_ONLY`(원본 확인·링크만 제공), `NOT_FOUND`, `NOT_APPLICABLE`, `TOOL_UNAVAILABLE`를 내부 확인한다. `FOUND_AND_DISPLAYABLE`은 **실제 본문 삽입 완료와 동일하지 않다.** 실제 미디어로 본문에 넣었는지 별도 확인하며 화면 렌더링을 관찰하지 못했다면 성공했다고 주장하지 않는다. `FOUND_LINK_ONLY`·`NOT_FOUND`는 이미지 제공으로 계산하지 않는다.

## 핵심 주제 이후의 깊이 확장

- **주제 자체를 충분히 설명한다.** 정의, 등장 배경, 실제 동작, 경계 조건, 흔한 오해, 실무 판단 기준 중 중요한 부분을 설명할 때 미완성으로 남기지 않는다.
- **더 알아볼 내용은 본문 설계 판단에 우선 연결한다.** 주제와 직접 관련된 심화 원리·설계 문제·다음 학습 키워드를 발견하면 **현재 소제목의 판단 기준이나 반례를 어떻게 보완하는지** 먼저 설명한다. 예를 들어 관련 서적의 공개 해설이 컴파일타임 의존성과 런타임 의존성의 차이를 다룬다면 인터페이스 기반 협력 단원에 반영하고, 단지 마지막에 서명·장 번호만 나열하지 않는다. 간결하게 추가할 만한 개념만 끝에 남긴다. 관련 한국어 개발 기술 글을 실제로 확인했다면 링크와 그 글의 핵심 내용도 함께 제공한다.
- **현재 주제와 심화 범위를 구분한다.** 연관 키워드가 있다고 모두 별도 강의로 길게 확장할 필요는 없다. 예를 들어 OOP 설명 뒤에는 객체의 책임 할당, 정보 전문가 원칙, Tell Don't Ask, 불변식, 조합과 상속의 선택 등을 학습 범위에 맞게 연결할 수 있다.
- **무조건적인 결말 템플릿은 만들지 않는다.** 심화할 내용이 많으면 작고 명료한 `더 알아볼 개념` 영역을, 필요가 없다면 생략한다. 본문 설명을 줄이고 링크만 나열하는 방식은 피한다.

## 응답 모드별 조사 밀도

- [요청 모드](response-modes.md)의 **EXPLAIN**에서는 주요 소제목별 출처와 실제 학습용 이미지를 적극 조사한다.
- **SUMMARIZE**에서는 핵심 사실과 주의 조건을 먼저 확인하고, 중요한 개념을 더 분명하게 해 줄 자료·이미지만 선별한다. 출처·이미지·긴 예제를 채우기 위해 핵심 요약을 늘리지 않는다.

## 설명 길이와 가독성

- **깊이와 길이는 다르다.** 인과관계·코드 동작·설계 판단은 충분한 문단으로 풀어 주지만, 정의·비교·핵심 조건·예외·심화 키워드 등은 **글머리표나 표를 적극 활용**할 수 있다.
- 같은 맥락의 문장을 매번 한 줄로 끊어 적지 않는다. 반대로 모든 항목을 3~5문장의 긴 설명으로 강제하지 않는다.
- 코드 블록 뒤에는 실제 실행·호출·상태 변화의 이유를 설명한다. 표를 사용할 때는 정상적인 Markdown 표 구조를 확인하여 깨진 빈 표나 열별 세로 나열을 방치하지 않는다.
- 소제목의 개수와 그림의 개수를 채우기 위해 내용을 반복하지 않는다.

## 품질 판정 예시

- **객체지향(OOP/OOD):** 일반 개인 개발 블로그와 관련된 한국 IT 기업 블로그의 실제 원리 설명을 찾아 활용한다. 클래스 그림보다 객체 간 메시지/협력과 책임 분배를 보여주는 **실제 이미지**를 우선 조사한다. 구현 코드 뒤에 변경·확장 판단과 관련 키워드(객체의 자율성, 정보 전문가, Tell Don't Ask 등)를 연결한다.
- **Spring Bean 생명주기:** 공식 레퍼런스로 호출 시점을 확인하고, 개인/기업 개발 기술 글의 실제 이미지가 적합한 경우 본문에 표시한다. 개발자가 왜 초기화·소멸 훅을 쓰는지와 주의 조건을 본문에서 설명한다.
- **DB MVCC:** DB 종류와 격리 수준에 따른 버전 가시성을 근거로 설명한다. 실제 이미지가 있다면 우선 이용하고, 둘 이상의 트랜잭션 상태가 잘 보이지 않을 때만 정확한 타임라인·표로 보충한다.

**확인되지 않은 사실·이미지·링크·실험 결과를 지어내지 않는다.** 이 문서는 자료 검색과 답변 작성의 행동 규칙이며, 실제 웹 접근이나 이미지 표시 성공을 보증하지 않는다.
