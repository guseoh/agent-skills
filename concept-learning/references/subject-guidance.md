# 분야별 깊이·예제 기준

이 문서는 공통 교수법의 범위를 **분야에 맞게 조절하는 참고 자료**다. 여러 분야를 한 번에 읽어 답변에 모두 넣지 않는다. 학습 로드맵, 특정 강의 PDF의 목차, 사용자 진도는 여기서 결정하지 않는다.

## Java·객체지향·JVM

- 타입이 허용하는 호출과 런타임 실제 객체의 메서드 선택, 참조값 복사와 객체 상태 수정, 메서드 호출·스택 프레임·힙 객체를 구분한다.
- 최소 두 객체/두 상태의 코드는 실제 호출 순서를 설명한 후 결과를 도출한다. `참조 변수 자체가 객체를 저장한다`, `Java는 참조를 전달한다` 같은 오해를 피한다.
- JVM 메모리 설명은 명세·HotSpot 구현·GC 관찰을 구분하고 수명/할당 위치를 과도하게 단순화하지 않는다.
- 예제: 부모 타입 참조로 오버라이딩 메서드를 호출할 때 컴파일 시점 타입 확인과 런타임 디스패치를 각각 설명한다.

## Spring Framework·Boot·MVC

- 요청 → DispatcherServlet·핸들러 선정 → 인자 해석/검증 → 애플리케이션 유스케이스 → 응답 변환·오류 처리라는 책임 경계를 설명한다. 실제 예외 핸들러·활성 설정은 확인 범위만 말한다.
- IoC/DI, Bean 생성과 생명주기, Boot 자동 구성, AOP/프록시, 선언적 트랜잭션의 조건을 구분한다.
- `@Transactional`은 실제 **프록시를 통과하는 호출 경계**에 주목한다. 같은 객체 내부의 자기 호출, 롤백 조건·전파, DB 커밋과 외부 효과의 분리를 필요할 때 설명한다.
- 사용자의 Spring REST API 학습 목표에서는 XML 설정·Thymeleaf 세부 실습·Servlet/JSP 직접 재구현에 과도한 시간을 쓰지 않는다. 역사와 프레임워크 발전 과정은 현재 원리를 이해하는 만큼만 연결한다.

## JPA·ORM·영속성

- 엔티티 상태(transient/managed/detached 등), 1차 캐시·변경 감지, flush, SQL 실행·트랜잭션 commit을 서로 구분한다.
- repository 호출만 보고 SQL이 정확히 언제 실행되는지, 트랜잭션이 반드시 있다는지 단정하지 않는다. 실제 접근 패턴과 쿼리·로그의 존재 여부를 밝힌다.
- N+1, 지연 로딩, fetch join, 배치/벌크 갱신, DB 제약과 ORM의 경계를 예제로 설명하고 선택 대안과 비용을 연결한다.

## Spring Security·웹 인증

- 인증과 인가, Filter Chain, SecurityContext, 세션/쿠키와 토큰의 신뢰 경계를 구분한다.
- 현재 학습이 인증 개념이면 JWT 상세 구현·필터 순서 전체·OAuth2 세부 확장까지 선행하지 않는다. 대신 구체적인 요청 정상/실패 경로를 필요 범위에서 짚는다.
- 객체 단위 인가, 자격 증명 보관, 세션 고정·CSRF·CORS는 클라이언트·배포 조건에 따라 판단한다.

## DB·SQL·동시성

- SQL 논리적 처리와 실제 실행 계획, 인덱스 물리 구조/선택도, MVCC의 가시성, Lock의 대기/경합 순서를 구분한다.
- 특정 DB·스토리지 엔진·격리 수준을 확인하지 않고 읽기 동작·갭 락·잠금 시간을 일반화하지 않는다.
- 두 트랜잭션의 명시적 타임라인, 데이터 버전, 제약 위반·중복 요청의 실패 조건을 구체적으로 설명한다.
- 실험 수치가 없으면 성능 향상·TPS 임계치를 임의로 만들지 않는다.

## Network·OS·Linux

- 프로토콜은 계층과 상태/타이밍(예: TCP 바이트 시퀀스·ACK·재전송)을 구별하고, HTTP 상태·캐시·TLS 등은 적용 조건을 명시한다.
- OS는 프로세스·스레드·스케줄링·가상 메모리·파일 디스크립터 등 실제 자원과 상태 전이 중심으로 설명한다.
- Linux는 기본적으로 개념 설명으로 시작하되 사용자가 실습을 요청했으면 `명령 → 예상 출력 → 실제 사용자 출력 해석 → 다음 판단`으로 전개한다. systemd의 `inactive`, `enabled`, 로그 기록의 의미를 섞지 않는다.
- WSL2처럼 환경 제약이 있다면 네트워크·systemd·커널 동작을 네이티브 서버의 운영 경험이라고 단정하지 않는다.

## 시스템 설계·아키텍처

- 요구와 불변식 → 핵심 흐름 → 데이터 모델·경계 → 실패/동시성 → 대안과 비용 → 검증 가능한 지표를 일관되게 설명한다.
- 가상 요구사항은 가정으로 명시하고, 한국 기업의 실제 운영 사례는 공개된 환경·부하·적용 이유를 보존한다. MSA·Redis·Kafka를 정답으로 강요하지 않는다.
- 설계 학습에서는 판단 근거와 대안 비교를 강화한다. 실전 문제 제출·퀴즈·시나리오 생성은 별도 요청에 따른다.

## AI·Agent·LLM

- 프롬프트·컨텍스트·모델·도구 호출·에이전트 루프·메모리·평가의 역할을 분리한다. 모델의 추론 결과와 실제 수행된 도구 행동을 구분한다.
- 정적 예시, 가상 비용 계산, 벤치마크 결과를 섞지 않는다. 권한·샌드박스·사용자 승인과 검증 하네스를 학습 맥락에 맞게 설명한다.

## 기술 연결의 분량

Java 주제에서 Spring/JPA 연결이 꼭 필요할 때는 2~4문장 정도로 압축하고 관련 소스 링크를 추가한다. 현재 주제를 독립적으로 이해하기 어려운 경우에만 연결 설명을 더 확장한다. 반대로 실제 백엔드 설계 주제에서는 깊이와 예제를 충분히 확보한다.
